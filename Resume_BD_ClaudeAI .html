    1.1 Contexte général : L'explosion des données

    Unités de mesure des données

    Les volumes de données sont devenus si importants qu'ils nécessitent de nouvelles unités de mesure :

    Unité Symbole Équivalence en Go
    Gigaoctet Go (GB) 1 Go
    Téraoctet To (TB) 1 000 Go
    Pétaoctet Po (PB) 1 000 000 Go (10⁶ Go)
    Exaoctet Eo (EB) 1 000 000 000 Go (10⁹ Go)
    Zettaoctet Zo (ZB) 1 000 000 000 000 Go (10¹² Go)
    Yottaoctet Yo (YB) 1 000 000 000 000 000 Go (10¹⁵ Go)

    💡 Chiffre clé : La production mondiale de données est estimée à environ 175 Zettaoctets par an d'ici la fin de 2025.

    Limites des systèmes traditionnels

    Les systèmes informatiques classiques (bases de données relationnelles traditionnelles) ne sont plus adaptés pour : - Stocker des volumes massifs de données - Traiter des données en temps réel - Gérer la variété des formats de données - Maintenir les performances face à la croissance exponentielle

    1.2 Définition du Big Data

    Le Big Data désigne : 1. L'ensemble des données massives, variées et générées à grande vitesse, dont le volume, la variété et la vélocité dépassent les capacités des systèmes informatiques traditionnels.

    1. Un ensemble de techniques et d'outils permettant de traiter des données trop volumineuses, trop complexes ou trop rapides pour être manipulées par des logiciels classiques de gestion de bases de données.

    📊 1. Volume

    Définition : Quantité massive de données générées chaque seconde dans le monde.

    Sources principales : - Réseaux sociaux - Capteurs IoT (Internet des Objets) - Transactions bancaires - Vidéos et contenus multimédias - Logs systèmes

    Enjeux : - Stocker efficacement ces volumes gigantesques - Traiter et analyser sans perte de performance - Réduire les coûts d'infrastructure et de stockage

    🖼️ [Illustration suggérée] : Graphique en barres montrant l'évolution exponentielle du volume de données de 2010 à 2025.

    ⚡ 2. Vélocité

    Définition : Vitesse à laquelle les données sont produites, transmises et analysées.

    Le Big Data ne se contente plus d'enregistrer les données, il doit les traiter en temps réel ou quasi temps réel.

    Exemples : - Flux de transactions bancaires (millions par seconde) - Données de capteurs IoT - Publications sur les réseaux sociaux - Logs de serveurs web

    Enjeux : - Gestion des flux de données continus (data streams) - Réduction de la latence - Maintien des performances malgré le débit élevé

    🖼️ [Illustration suggérée] : Schéma de flux de données en temps réel montrant des capteurs IoT → ingestion → traitement → visualisation en quelques millisecondes.

    🎨 3. Variété

    Définition : Diversité des types et formats de données collectées.

    Les données ne sont plus uniquement structurées (comme dans les bases relationnelles), mais aussi semi-structurées et non structurées.

    Types de données : - Structurées : Bases de données SQL, fichiers CSV - Semi-structurées : JSON, XML, logs - Non structurées : Textes, images, vidéos, audio, emails

    Enjeu principal : - Nécessité d'outils hétérogènes capables de gérer tous ces formats

    🖼️ [Illustration suggérée] : Diagramme circulaire montrant la répartition des types de données (structurées 20%, semi-structurées 30%, non structurées 50%).

    ✅ 4. Véracité

    Définition : Qualité, fiabilité et précision des données.

    Toutes les données ne sont pas exactes. Certaines peuvent être : - Incomplètes - Erronées - Redondantes - Biaisées

    Enjeux : - Détection et nettoyage des erreurs - Validation des données avant analyse - Fiabilisation des sources

    🖼️ [Illustration suggérée] : Pipeline de nettoyage de données montrant : données brutes → détection d'anomalies → nettoyage → données fiables.

    💎 5. Valeur

    Définition : Capacité à transformer les données brutes en informations utiles, décisions stratégiques ou avantages concurrentiels.

    💡 C'est le V le plus important !

    Enjeux : - Transformer les données en insights actionnables - Assurer un retour sur investissement (ROI) - Créer de la valeur business

    Exemples de création de valeur : - Recommandations personnalisées (Netflix, Amazon) - Détection de fraudes bancaires - Optimisation de la chaîne logistique - Prédictions en santé publique

    📘 Partie 2 : L'écosystème Hadoop et MapReduce

    2.1 Introduction à Hadoop

    Définition

    Hadoop est un framework open source développé par Apache, conçu pour : - Le stockage de très grandes quantités de données - Le traitement distribué sur des clusters de serveurs standards

    Composants principaux : - HDFS (Hadoop Distributed File System) : stockage distribué - MapReduce : paradigme de traitement parallèle

    Objectifs principaux

    1. Stocker de gros volumes de données non structurées
    2. Traiter ces données de manière parallèle et rapide
    3. Assurer la tolérance aux pannes

    🖼️ [Illustration suggérée] : Logo d'Hadoop (éléphant jaune) avec les mots-clés : Distribué, Évolutif, Tolérant aux pannes.

    2.2 Histoire et origines de Hadoop

    🎯 Contexte (début des années 2000)

    • Croissance rapide du Web
    • Explosion du volume de données (pages, clics, recherches)
    • Besoin de systèmes capables de traiter ces volumes

    🔬 Technologies clés de Google

    2003 - Google File System (GFS) - Système de fichiers distribué - Gestion de données massives sur des milliers de serveurs

    2004 - MapReduce - Modèle de programmation parallèle - Traitement de grandes quantités de données

    👨‍💻 Doug Cutting et Mike Cafarella : Pères fondateurs

    Problème : Faire évoluer Nutch (moteur de recherche open source) à grande échelle.

    Solution : Adapter les idées de Google - Implémentation open source de GFS → HDFS - Implémentation open source de MapReduce → MapReduce Hadoop

    Naissance : Projet Hadoop créé vers 2005-2006

    Origine du nom : "Hadoop" vient du jouet en peluche (un éléphant jaune) du fils de Doug Cutting.

    🐘 L'éléphant est depuis devenu le symbole officiel du framework.

    📈 Adoption par Yahoo! (2006-2008)

    2006 : Doug Cutting rejoint Yahoo!

    Objectifs de Yahoo! : - Gérer des pétaoctets de données web - Stockage distribué - Calcul parallèle (analyse de logs, recherche)

    2008 : Yahoo! met en production le plus grand cluster Hadoop du monde à l'époque : - Plus de 10 000 cœurs de calcul - Traitement de téraoctets de données par jour

    🏛️ Intégration dans la fondation Apache (2008)

    Hadoop devient un projet de haut niveau (Top-Level Project) de la Fondation Apache.

    Avantages : - Gouvernance communautaire - Évolution open source - Création d'un écosystème de projets associés

    🚀 Expansion de l'écosystème (2009-2013)

    Hadoop devient la colonne vertébrale du Big Data.

    Distributions commerciales : - Cloudera (2009) - Hortonworks (2011) - MapR (2011) - IBM BigInsights (2011)

    Composants majeurs créés :

    Année Composant Description
    2009 Hive Requêtes SQL sur Hadoop
    2009 Pig Langage de scripts pour traitement de données
    2010 HBase Base NoSQL distribuée
    2011 Zookeeper, Oozie Coordination et orchestration
    2012 YARN Nouvelle architecture pour gestion des ressources

    📊 Évolutions majeures : Hadoop 2.x et 3.x

    Hadoop 2.x (2013-2017)

    ✅ Introduction de YARN - Remplace JobTracker/TaskTracker - Permet d'exécuter plusieurs types d'applications (pas seulement MapReduce) - Meilleure gestion des ressources et scalabilité

    Hadoop 3.x (2018-aujourd'hui)

    ✅ Optimisations majeures : - Erasure Coding : économie d'espace disque - Support GPU et containers (Docker, Kubernetes) - Performances accrues - Compatibilité cloud

    2.3 Composants principaux de l'écosystème Hadoop

    🗄️ HDFS (Hadoop Distributed File System)

    Définition : Système de fichiers distribué offrant un accès haut débit aux données.

    Caractéristiques : - S'étend sur tous les nœuds d'un cluster - Relie les systèmes de fichiers locaux de plusieurs nœuds - Transforme ces systèmes en un seul grand système de fichiers distribué

    🖼️ [Illustration suggérée] : Schéma montrant plusieurs serveurs physiques reliés formant un système de fichiers unique logique HDFS.

    ⚙️ MapReduce

    Définition : Framework de traitement distribué des données à grande échelle.

    Principe : Diviser les tâches en deux étapes principales :

    1. Map : Traitement parallèle et transformation des données en paires (clé, valeur)
    2. Reduce : Agrégation et synthèse des résultats produits par la phase Map

    🔧 YARN (Yet Another Resource Negotiator)

    Rôle : Gestionnaire de ressources et planificateur de tâches du cluster.

    Avantages : - Séparation de la gestion des ressources de la logique applicative - Support de multiples moteurs d'exécution (MapReduce, Spark, Tez, etc.)

    2.4 HDFS (Hadoop Distributed File System)

    🎯 Objectif

    HDFS est conçu pour stocker de très grandes quantités de données de manière : - Distribuée : répartie sur plusieurs machines - Fiable : tolérante aux pannes - Évolutive : peut croître en ajoutant des nœuds

    📋 Caractéristiques principales

    ✅ Système distribué, évolutif, tolérant aux pannes et à haut débit

    ✅ Accès aux données via MapReduce

    ✅ Découpage en blocs (splits) - Fichiers découpés en blocs de 128 Mo (par défaut) - Chaque bloc est répliqué (3 répliques par défaut)

    ✅ Opérations limitées : - Création, suppression, copie : ✅ - Modification : ❌ (Write Once, Read Many - WORM)

    ✅ Lecture en flux continu (streaming reads) - Optimisé pour lectures séquentielles, pas pour accès aléatoires

    ✅ Principe de localité des données - Traiter les données là où elles sont stockées - Réduit le transfert de données sur le réseau

    🖼️ [Illustration suggérée] : Schéma montrant un gros fichier découpé en blocs de 128 Mo distribués sur différents serveurs avec leurs répliques.

    🎓 Master : NameNode

    Rôle : Cerveau du système de fichiers HDFS

    Responsabilités : - Gère l'espace de noms du système de fichiers - Stocke les métadonnées : - FsImage : Image du système de fichiers (structure) - EditLog : Journal des modifications - Régule l'accès des clients aux fichiers - Ne stocke PAS les données elles-mêmes, seulement les métadonnées

    ⚠️ Point critique : Le NameNode est un point unique de défaillance (SPOF) dans Hadoop 1.x

    👷 Slave : DataNode

    Rôle : Stocke réellement les blocs de données

    Caractéristiques : - Plusieurs DataNodes par cluster - Gère le stockage physique attaché aux nœuds - Envoie périodiquement un rapport d'état (heartbeat) au NameNode - Exécute les opérations de lecture/écriture demandées par les clients

    🚀 Démarrage du NameNode

    Séquence au démarrage :

    1. Le NameNode lit le fsimage en mémoire
    2. Le NameNode applique les modifications du editlog
    3. Le NameNode attend les rapports de blocs des DataNodes - Note : Le NameNode ne stocke PAS les localisations physiques des blocs - Ces informations sont reçues des DataNodes au démarrage
    4. Le NameNode quitte le mode sans échec (SafeMode) lorsque 99,9% des blocs disposent d'au moins une copie reconnue

    ⏱️ SafeMode : Mode de protection pendant lequel HDFS est en lecture seule.

    📝 Ajout d'un fichier à HDFS

    Processus :

    1. Le fichier est ajouté à la mémoire du NameNode en enregistrant les informations dans le fichier editlog

    2. Les données sont écrites en blocs sur les DataNodes - Le premier DataNode commence une copie en chaîne vers deux autres DataNodes - Pipeline : Client → DataNode1 → DataNode2 → DataNode3

    3. Condition de succès : - Si au moins une écriture réussit pour chaque bloc, l'opération d'écriture est considérée comme réussie - Les réplications manquantes seront complétées par le NameNode ultérieurement

    🖼️ [Illustration suggérée] : Diagramme de séquence montrant le flux : Client → NameNode (métadonnées) → DataNode1 → DataNode2 → DataNode3 (pipeline de réplication).

    🔧 Secondary NameNode

    ⚠️ Attention : Malgré son nom, ce n'est PAS une solution de haute disponibilité !

    Rôle : Assistant du NameNode principal

    Fonction : - Pendant le fonctionnement, le NameNode principal ne peut pas fusionner les fichiers fsImage et editlog - Cette tâche est effectuée par le Secondary NameNode périodiquement

    Processus : 1. Le Secondary NameNode copie le nouveau edit log depuis le NameNode principal 2. Il fusionne ce journal avec le fichier fsImage 3. Il renvoie le nouveau fsImage au NameNode principal

    Avantage : - Permet un démarrage plus rapide du NameNode - Réduit la taille de l'editlog

    🖼️ [Illustration suggérée] : Schéma montrant NameNode et Secondary NameNode avec les échanges de fsImage et editlog entre eux.

    🏥 HDFS-2 : Haute disponibilité (High Availability)

    Problème de Hadoop 1.x : Le NameNode était un point unique de défaillance (SPOF)

    Solution HDFS-2 : Introduction de la Haute Disponibilité (HA)

    Architecture HA :

    1. NameNode Actif (Active NameNode) - Gère les opérations du système de fichiers - Enregistre les modifications sur les JournalNodes

    2. NameNode en veille (Standby NameNode) - Maintient une copie synchronisée de l'état du NameNode actif - Prêt à prendre le relais instantanément en cas de panne

    3. JournalNodes (au moins 3) - Stockent les transactions du système de fichiers - Le NameNode actif écrit sur au moins 3 JournalNodes - Le Standby NameNode lit ces transactions pour rester à jour

    4. DataNodes - Envoient les localisations des blocs et heartbeats aux deux NameNodes

    Avantage : - ✅ Basculement rapide en cas de panne - ✅ Pas de perte de données - ✅ Disponibilité quasi continue

    🖼️ [Illustration suggérée] : Architecture HA avec Active NameNode, Standby NameNode, 3 JournalNodes au milieu, et DataNodes communiquant avec les deux NameNodes.

    🗂️ HDFS fédéré (Federated HDFS)

    Problème : Dans un cluster traditionnel, un seul NameNode gère toutes les métadonnées, ce qui limite la scalabilité.

    Solution : HDFS fédéré (introduit dans Hadoop 2.x)

    Principe : - Plusieurs NameNodes indépendants dans un même cluster - Chaque NameNode gère un espace de noms (namespace) indépendant - DataNodes partagés entre tous les NameNodes

    Structure : - Namespace 1 → NameNode1 → Métadonnées NS1 - Namespace 2 → NameNode2 → Métadonnées NS2 - Namespace 3 → NameNode3 → Métadonnées NS3 - Tous utilisent le même pool de DataNodes

    Avantages : - ✅ Meilleure scalabilité (répartition de la charge des métadonnées) - ✅ Isolation des namespaces (une panne n'affecte qu'un namespace) - ✅ Gestion de très gros clusters

    🖼️ [Illustration suggérée] : Schéma montrant 3 NameNodes au sommet, chacun gérant son namespace, et en dessous un pool commun de DataNodes.

    2.5 MapReduce

    🎯 Définition

    MapReduce est un : - Modèle de programmation développé par Google - Mécanisme de traitement distribué implémenté dans Hadoop - Permet de traiter efficacement de grandes quantités de données sur un cluster

    💡 Principes fondamentaux

    1. Gestion des ressources et planification des tâches
    2. Amener la fonction vers les données (et non l'inverse) - Évite de déplacer des téraoctets de données sur le réseau - L'application est distribuée vers les ressources de calcul où les données sont stockées

    🖼️ [Illustration suggérée] : Schéma comparatif montrant l'ancien modèle (déplacement des données vers le programme) vs MapReduce (déplacement du programme vers les données).

    🔄 Les trois phases de MapReduce

    1️⃣ Phase Map (Mappers)

    Rôle : Traitement initial et transformation

    Fonctionnement : - Chaque nœud du cluster lit une portion des données d'entrée - Applique une fonction Map à chaque élément - Produit des paires clé/valeur <clé, valeur> - Un mapper est généralement un programme relativement petit avec une tâche simple

    Exemple : Pour compter des mots

    Input : "Tigre Singe Tigre"
Output Map : (Tigre, 1), (Singe, 1), (Tigre, 1)

    2️⃣ Phase Shuffle (Mélange et tri)

    Rôle : Intermédiaire entre Map et Reduce

    Fonctionnement : - Transfère les paires intermédiaires depuis les nœuds Map vers les nœuds Reduce - Regroupe toutes les valeurs associées à une même clé - Trie les données par clé

    Exemple :

    Avant Shuffle : (Tigre, 1), (Chat, 1), (Tigre, 1), (Chat, 1), (Tigre, 1)
Après Shuffle : (Chat, [1, 1]), (Tigre, [1, 1, 1])

    🔧 Cette phase est automatique et gérée par le framework MapReduce

    3️⃣ Phase Reduce (Reducers)

    Rôle : Agrégation et production du résultat final

    Fonctionnement : - De petits programmes qui agrègent toutes les valeurs associées à une clé - Les paires ayant la même clé sont envoyées au même Reducer - La fonction Reduce combine ou agrège les valeurs pour produire le résultat final

    Exemple :

    Input Reduce : (Chat, [1, 1]), (Tigre, [1, 1, 1])
Output Reduce : (Chat, 2), (Tigre, 3)

    🏗️ Architecture MapReduce v1

    🎓 JobTracker (Maître)

    Caractéristiques : - Unique dans le cluster - Situé généralement sur le NameNode (ou serveur séparé)

    Rôles principaux : 1. Planifie les tâches Map et Reduce sur les nœuds disponibles 2. Surveille leur exécution 3. Gère les échecs et relance les tâches en cas de panne 4. Gère l'allocation des ressources (CPU, mémoire)

    ⚠️ Point critique : Si le JobTracker tombe en panne, tout le job échoue (SPOF - Single Point Of Failure)

    👷 TaskTracker (Esclaves)

    Caractéristiques : - Un processus TaskTracker s'exécute sur chaque nœud du cluster

    Rôles : 1. Exécute les tâches Map et Reduce envoyées par le JobTracker 2. Signale périodiquement son état au JobTracker via des heartbeats

    Gestion des ressources : - Chaque TaskTracker a un nombre fixe de slots : - Map slots - Reduce slots - Une fois les slots occupés, le nœud ne peut plus accepter de nouvelles tâches

    Tolérance aux pannes : - Si un TaskTracker échoue, le JobTracker redistribue ses tâches à un autre nœud

    🖼️ [Illustration suggérée] : Architecture avec 1 JobTracker central (maître) et plusieurs TaskTrackers (esclaves) sur différents nœuds.

    🔄 Processus d'exécution d'un job MapReduce

    Acteurs :

    1. Client : Soumet les jobs MapReduce

    2. JobTracker : Coordonne l'exécution - Découpe le job en tâches Map et Reduce - Attribue ces tâches aux différents nœuds

    3. TaskTracker : Exécute les tâches - Fonctions Map sur les données locales - Fonctions Reduce sur les résultats intermédiaires

    Flux d'exécution :

    Client → JobTracker → TaskTrackers (Map) → Shuffle → TaskTrackers (Reduce) → Résultat

    🖼️ [Illustration suggérée] : Diagramme de séquence montrant l'interaction Client → JobTracker → TaskTrackers avec les différentes phases.

    ⚠️ Limitations de MapReduce v1

    Problèmes identifiés :

    1. ❌ Scalabilité limitée (passage à grande échelle) - JobTracker unique devient un goulot d'étranglement - Limite à ~4000 nœuds dans le cluster

    2. ❌ Utilisation inefficace des ressources - Slots Map et Reduce fixes - Un slot Map vide ne peut pas être utilisé par Reduce (et vice-versa) - Gaspillage de ressources

    3. ❌ Manque de support pour d'autres moteurs - Uniquement MapReduce supporté - Impossible d'exécuter d'autres frameworks (Spark, Tez, etc.) - Pas de traitement en temps réel (streaming)

    🖼️ [Illustration suggérée] : Schéma montrant les slots Map et Reduce fixes avec certains slots vides mais inutilisables par l'autre type de tâche.

    2.6 YARN (Yet Another Resource Negotiator)

    🎯 Définition et contexte

    YARN est le gestionnaire de ressources introduit dans Hadoop 2 pour : - Améliorer la scalabilité - Augmenter la flexibilité - Optimiser l'efficacité du traitement des données dans le cluster

    Innovation majeure : Sépare la gestion des ressources de la logique de traitement

    Conséquence : Hadoop peut supporter plusieurs moteurs d'exécution simultanément (MapReduce, Spark, Tez, etc.)

    🏗️ Architecture de YARN

    YARN introduit trois composants principaux :

    1️⃣ ResourceManager (RM) - Le maître du cluster

    Rôle : - Gère toutes les ressources globales du cluster - Décide quelle application obtient quelles ressources

    Sous-composants : - Scheduler : Alloue les ressources (CPU, mémoire) aux applications - ApplicationsManager : Gère le cycle de vie des applications

    💡 Un seul ResourceManager par cluster (peut être en HA)

    2️⃣ NodeManager (NM) - Gestionnaire local

    Rôle : - Présent sur chaque nœud du cluster - Exécute les conteneurs (containers) - Surveille les ressources locales (CPU, mémoire, disque) - Envoie des rapports d'état au ResourceManager

    💡 Équivalent moderne du TaskTracker mais plus flexible

    3️⃣ ApplicationMaster (AM) - Coordinateur d'application

    Rôle : - Chaque application (job MapReduce, application Spark) a son propre ApplicationMaster - Négocie les ressources avec le ResourceManager - Coordonne les tâches de l'application - Surveille l'exécution des tâches

    💡 Contrairement au JobTracker unique, chaque job a son propre AM, ce qui améliore la scalabilité

    🔄 Flux d'exécution dans YARN

    Étapes :

    1. Le client soumet une application au ResourceManager

    2. Le ResourceManager alloue un conteneur pour l'ApplicationMaster

    3. L'ApplicationMaster démarre et demande des ressources au ResourceManager

    4. Le ResourceManager alloue des conteneurs sur les NodeManagers

    5. L'ApplicationMaster lance les tâches dans les conteneurs

    6. Les NodeManagers exécutent les tâches et rapportent leur état

    7. L'ApplicationMaster collecte les résultats et libère les ressources

    2.7 Apache Pig

    🎯 Définition et contexte

    Apache Pig est un : - Langage de flux de données de haut niveau - Développé initialement par Yahoo! en 2006 - Intégré à l'écosystème Apache Hadoop comme projet open source

    Objectif principal : Simplifier le développement et l'exécution des tâches de traitement de données sans écrire d'implémentations Java complexes en MapReduce.

    💡 Principe fondamental

    Pig Latin : Langage de script déclaratif

    Avantages : - ✅ Environ 10 lignes de code Pig = 200 lignes de code MapReduce - ✅ Approche multi-requêtes : Une seule requête Pig peut effectuer plusieurs tâches MapReduce - ✅ Abstraction de la complexité de MapReduce

    💡 Analogie : Pig est à MapReduce ce que SQL est à la manipulation manuelle de fichiers

    🎯 Objectifs clés d'Apache Pig

    1️⃣ Rendre les traitements Big Data plus accessibles

    • Analystes non-développeurs peuvent écrire des pipelines de données
    • Pas besoin de connaître les détails de MapReduce
    • Syntaxe intuitive et expressive

    2️⃣ Augmenter la productivité

    • Un script Pig peut être 10 à 20 fois plus court qu'un programme MapReduce équivalent en Java
    • Développement plus rapide
    • Maintenance simplifiée

    3️⃣ Assurer une exécution distribuée évolutive

    • Pig s'appuie sur Hadoop et YARN
    • Transformation automatique : Script Pig Latin → Plan logique → Plan physique → Jobs MapReduce
    • Exécution sur le cluster

    4️⃣ Manipuler différents types de données

    • Pig n'impose aucun modèle de données strict
    • Adapté aux données :
    • Structurées : CSV, TSV
    • Semi-structurées : JSON, XML
    • Non-structurées : logs, texte brut

    5️⃣ Offrir une extensibilité maximale

    • Fonctions Définies par l'Utilisateur (UDF - User Defined Functions)
    • Support de multiples langages :
    • ✅ Java
    • ✅ Python
    • ✅ Ruby
    • ✅ JavaScript

    ⚖️ Apache Pig vs MapReduce

    Critère Apache Pig MapReduce
    Niveau d'abstraction Haut niveau (Pig Latin) Bas niveau (Java)
    Facilité d'utilisation ✅ Très facile, scripts courts ❌ Complexe, beaucoup de code
    Approche Dataflow (flux de transformations) Algorithmique (Map + Reduce)
    Type de code Scripts déclaratifs Code Java impératif
    Temps de développement ✅ Rapide ❌ Lent
    Extensibilité UDF (Python, Java, Ruby) Extensions Java uniquement
    Exécution Traduit en MapReduce, Tez ou Spark MapReduce uniquement
    Cas d'utilisation ETL, nettoyage, agrégations, logs Algorithmes complexes nécessitant contrôle total
    Performance Bonne (optimisée automatiquement) Très bonne si bien codé
    Courbe d'apprentissage ✅ Faible ❌ Élevée
    Flexibilité des données Très flexible (structurées, semi-structurées, logs) Dépend du développeur

    🔧 Utilisation d'Apache Pig

    Apache Pig est utilisé pour :

    1. Traiter d'énormes ensembles de données : - Journaux Web (logs) - Données en ligne continues (streaming)

    2. Plateformes de recherche - Où différents types de données doivent être traités

    3. Traitement en temps réel : - Données pour algorithmes de Machine Learning - Activités des utilisateurs sur les réseaux sociaux

    📊 Cas d'usage réels :

    Yahoo! : - Utilise Pig pour ~40% de ses tâches - Flux d'actualités - Moteur de recherche

    Twitter/X : - Extraction et analyse rapide des tweets - Analyse des retweets - Tendances comportementales - Génération de recommandations immédiates

    🏗️ Architecture Apache Pig

    Composants principaux :

    1. Pig Latin - Langage de haut niveau pour écrire les scripts - Définit les opérations : chargement, filtrage, transformation, jointure, agrégation

    2. Parser (Analyseur) - Vérifie la syntaxe du script - Génère un graphe de flux de données (DAG - Directed Acyclic Graph)

    3. Optimizer (Optimiseur) - Optimise le plan logique - Réorganise les opérations pour améliorer les performances

    4. Compiler (Compilateur) - Transforme le plan logique optimisé en plan physique - Génère les jobs MapReduce, Tez ou Spark

    5. Execution Engine (Moteur d'exécution) - Soumet les jobs au cluster Hadoop - Exécute via MapReduce, Tez ou Spark

    🖼️ [Illustration suggérée] : Pipeline de traitement : Script Pig Latin → Parser → Optimizer → Compiler → Execution Engine → Hadoop Cluster.

    📝 Exemple de script Pig Latin

    Objectif : Compter le nombre d'occurrences de chaque mot dans un fichier

    -- Charger les données
lines = LOAD '/data/input.txt' AS (line:chararray);

-- Tokeniser (découper en mots)
words = FOREACH lines GENERATE FLATTEN(TOKENIZE(line)) AS word;

-- Grouper par mot
grouped = GROUP words BY word;

-- Compter les occurrences
wordcount = FOREACH grouped GENERATE group AS word, COUNT(words) AS count;

-- Stocker le résultat
STORE wordcount INTO '/data/output' USING PigStorage(',');

    Équivalent MapReduce : ~200 lignes de code Java !

    2.8 Apache Hive

    🎯 Définition

    Apache Hive est une infrastructure d'entrepôt de données (data warehouse) construite au-dessus de Hadoop pour : - Effectuer des requêtes SQL-like sur de grandes quantités de données - Fournir une abstraction SQL pour les données stockées dans HDFS - Permettre aux analystes familiers avec SQL d'exploiter Hadoop sans connaître MapReduce

    Langage : HiveQL (Hive Query Language), similaire à SQL

    💡 Principe fondamental

    Hive transforme :

    Requêtes HiveQL → Jobs MapReduce (ou Tez/Spark) → Exécution sur Hadoop

    Avantage : Les utilisateurs écrivent du SQL, Hive gère la complexité de MapReduce

    🏗️ Architecture de Hive

    Composants principaux :

    1. Hive Client - CLI (Command Line Interface) - JDBC/ODBC : Connexion depuis des outils externes - Beeline : Client recommandé (plus sécurisé)

    2. Hive Services - Driver : Gère le cycle de vie des requêtes - Compiler : Transforme HiveQL en plan d'exécution - Optimizer : Optimise le plan - Execution Engine : Exécute le plan sur Hadoop

    3. Metastore - Base de données (MySQL, PostgreSQL, Derby) stockant :

      • Schémas des tables
      • Métadonnées (colonnes, types, partitions)
      • Localisation des données dans HDFS

    4. Hadoop - HDFS : Stockage des données - MapReduce/Tez/Spark : Exécution des requêtes

    🖼️ [Illustration suggérée] : Architecture Hive avec Client → Driver → Metastore → Execution Engine → HDFS.

    📊 Cas d'usage de Hive

    ✅ Requêtes ad-hoc sur de grandes quantités de données

    ✅ Data warehousing : Création d'entrepôts de données

    ✅ Reporting et analytique : Génération de rapports business

    ✅ ETL : Extraction, transformation, chargement de données

    ✅ Analyse de logs : Requêtes sur des téraoctets de logs

    Limitations : - ❌ Pas adapté au traitement en temps réel (latence élevée) - ❌ Pas conçu pour les transactions OLTP (pas de UPDATE/DELETE efficace) - ✅ Optimisé pour les lectures massives (OLAP)

    2.9 Apache Sqoop

    🎯 Définition

    Apache Sqoop (SQL to Hadoop) est un outil conçu pour : - Transférer efficacement des données entre Hadoop et les bases de données relationnelles - Importer des données depuis des SGBDR vers HDFS/Hive/HBase - Exporter des données depuis Hadoop vers des SGBDR

    Prononciation : "Scoop" (comme une pelle)

    💡 Principe de fonctionnement

    Import :

    Base de données SQL → Sqoop → MapReduce → HDFS/Hive/HBase

    Export :

    HDFS/Hive/HBase → Sqoop → MapReduce → Base de données SQL

    Particularité : Sqoop utilise uniquement des Mappers (pas de Reducers) - Les données sont lues/écrites directement - Pas besoin d'agrégation

    🏗️ Architecture Sqoop 2

    1️⃣ Sqoop Client

    Deux modes d'accès : - CLI (Command Line Interface) : Ligne de commande - Browser (Interface Web) : Interface REST/UI

    Ces deux méthodes envoient les requêtes vers le serveur Sqoop.

    2️⃣ Sqoop Server

    Intermédiaire intelligent entre le client et les systèmes sources/destination.

    Modules : - REST : Interface RESTful pour clients externes - UI : Interface graphique de gestion - Job Manager : Création, configuration, exécution et suivi des jobs - Connector Manager : Gestion des connecteurs - Connectors : Modules spécialisés pour bases relationnelles, data warehouses, etc. - Metadata : Informations sur jobs, connexions, exécutions (stockées dans Metadata Repository)

    3️⃣ Sources et Destinations

    • Bases de données relationnelles (MySQL, PostgreSQL, Oracle, SQL Server)
    • Data Warehouses (Teradata, Netezza)
    • Hadoop (HDFS, Hive, HBase)

    4️⃣ Hadoop

    Lorsque Sqoop exécute un job : - Le serveur soumet des Map Tasks au cluster Hadoop - Les mappers lisent/écrivent les données - Les données transitent par HDFS, HBase ou Hive

    🖼️ [Illustration suggérée] : Architecture complète Sqoop 2 avec User → Client (CLI/Browser) → Server (modules) → Sources/Hadoop.

    🔄 Fonctionnement de Sqoop (Import)

    Étapes :

    Étape 1 : Connexion - Sqoop se connecte à la base de données via JDBC

    Étape 2 : Découverte du schéma - Sqoop récupère : - Colonnes - Types de données - Clé primaire - Contraintes

    Étape 3 : Partitionnement - Pour paralléliser, Sqoop découpe les données selon une colonne split-by - Exemple : colonne id de 1 à 100 000 → divisée en 4 ranges

    Étape 4 : Exécution MapReduce - Chaque mapper exécute une requête SQL différente : sql Mapper 1: SELECT * FROM employees WHERE id >= 1 AND id < 25000; Mapper 2: SELECT * FROM employees WHERE id >= 25000 AND id < 50000; Mapper 3: SELECT * FROM employees WHERE id >= 50000 AND id < 75000; Mapper 4: SELECT * FROM employees WHERE id >= 75000 AND id <= 100000;

    🖼️ [Illustration suggérée] : Diagramme montrant 1 table SQL divisée en 4 ranges → 4 mappers → données écrites dans HDFS.

    2.10 Apache Flume

    🎯 Définition

    Apache Flume est un service distribué, fiable et disponible pour : - Collecter efficacement des données de flux continu - Agréger ces données - Transférer de grandes quantités de données de log

    Cas d'usage typique : Ingestion de logs en temps réel vers HDFS

    💡 Concepts clés

    Agent Flume : Processus JVM qui héberge les composants par lesquels les événements transitent.

    Event (Événement) : Unité de base des données dans Flume - Header : Paires clé/valeur (métadonnées) - Body : Tableau de bytes (données brutes)

    🏗️ Architecture d'un Agent Flume

    Un agent Flume contient 3 composants essentiels :

    ┌────────────────────────────────────────────────────────────────┐
│                      AGENT FLUME                               │
│                                                                │
│  ┌──────────┐      ┌──────────┐      ┌──────────┐            │
│  │          │      │          │      │          │            │
│  │  SOURCE  │─────▶│ CHANNEL  │─────▶│   SINK   │            │
│  │          │      │(Buffer)  │      │          │            │
│  └──────────┘      └──────────┘      └──────────┘            │
│       │                 │                  │                  │
│       ▼                 ▼                  ▼                  │
│  ┌──────────┐      ┌──────────┐      ┌──────────┐            │
│  │ Exec     │      │ Memory   │      │  HDFS    │            │
│  │ Syslog   │      │ File     │      │  HBase   │            │
│  │ HTTP     │      │ Kafka    │      │  Kafka   │            │
│  │ Kafka    │      │          │      │  Logger  │            │
│  └──────────┘      └──────────┘      └──────────┘            │
│                                                                │
│  ┌──────────────────────────────────────────────────────┐     │
│  │           INTERCEPTORS (optionnel)                   │     │
│  │  - Ajout timestamp                                   │     │
│  │  - Filtrage par type                                 │     │
│  │  - Enrichissement métadonnées                        │     │
│  └──────────────────────────────────────────────────────┘     │
└────────────────────────────────────────────────────────────────┘

    1️⃣ Source (Entrée des données)

    Rôle : Point d'entrée des données dans l'agent

    Types de Sources :

    Source Description
    Exec Source Exécute une commande Unix (ex: tail -F log.txt)
    Spooling Directory Surveille un répertoire pour nouveaux fichiers
    Syslog Source Réception de logs syslog
    HTTP Source Reçoit des événements via HTTP POST
    Kafka Source Consomme depuis un topic Kafka
    Avro Source Reçoit des événements d'un autre agent Flume

    2️⃣ Channel (Buffer/Canal)

    Rôle : Cœur de l'agent, gère la fiabilité et la tolérance aux pannes

    Fonctions : - Agit comme file d'attente entre Source et Sink - Réalise la transaction (garantit que les données ne sont pas perdues) - Empêche le backpressure (contre-pression)

    Types de Channels :

    Channel Avantages Inconvénients
    Memory Très rapide Perte de données en cas de crash
    File Fiable (persistant sur disque) Plus lent
    Kafka Haute scalabilité, résilient Nécessite Kafka

    ⚠️ Sans canal, impossible de connecter source et sink !

    3️⃣ Sink (Sortie des données)

    Rôle : Écrit les événements du canal vers leur destination finale

    Types de Sinks :

    Sink Destination
    HDFS Sink Écriture dans HDFS (Parquet, SequenceFile, TextFile)
    HBase Sink Insertion dans tables HBase
    Kafka Sink Publication dans Kafka
    File Roll Sink Stockage dans fichiers locaux
    Logger Sink Console / logs (debug)
    ElasticSearch Sink Indexation dans ElasticSearch

    🖼️ [Illustration suggérée] : Schéma d'un agent Flume avec Source → Channel → Sink.

    🔧 Composants additionnels dans un agent

    Intercepteurs

    Rôle : - Interceptent, modifient ou filtrent les événements avant qu'ils entrent dans le canal - Traitement léger sur chaque événement - Enrichissement des données

    Cas d'usage : - Ajouter un timestamp aux événements - Filtrer uniquement les logs de type ERROR - Ajouter des métadonnées (source IP, application)

    Sélecteurs de canal (Channel Selectors)

    Rôle : Routage des événements entre une Source et plusieurs Channels

    Types : - Replicating : Copie chaque événement dans tous les canaux - Multiplexing : Route vers un canal spécifique basé sur une règle

    Sink Processors

    Rôle : Gèrent le comportement d'un sink

    Types : - Failover : Si un sink échoue, un autre prend le relais - Load Balancing : Répartit la charge entre plusieurs sinks

    🌊 Modes de circulation des données (Data Flow Patterns)

    1️⃣ Flux multi-sauts (Multi-hop Flow)

    Principe : Un événement traverse plusieurs agents Flume successifs avant d'atteindre sa destination finale.

    ┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
│ Agent 1  │─────▶│ Agent 2  │─────▶│ Agent 3  │─────▶│   HDFS   │
│ (Source) │      │ (Relais) │      │ (Relais) │      │          │
└──────────┘      └──────────┘      └──────────┘      └──────────┘
   Serveur           Serveur           Serveur          Stockage
   Web 1             Web 2             Agrégation       Final

    Structure :

    Agent 1 (Source) → Agent 2 (Relais) → Agent 3 (Relais) → HDFS

    Cas d'usage : - Collecte distribuée géographiquement - Agrégation progressive des données

    2️⃣ Fan-out (Flux en éventail)

    Principe : Une seule source envoie les événements vers plusieurs canaux ou destinations.

                            ┌──────────┐
                        │ Source   │
                        │ Unique   │
                        └────┬─────┘
                             │
                ┌────────────┼────────────┐
                │            │            │
                ▼            ▼            ▼
           ┌────────┐   ┌────────┐   ┌────────┐
           │ HDFS   │   │ HBase  │   │ Kafka  │
           └────────┘   └────────┘   └────────┘
           Archive      Temps réel   Streaming

    Types : - Réplication : Événements dupliqués, chaque canal reçoit une copie complète - Multiplexage : Événements routés vers un canal précis selon une règle

    Cas d'usage : - Archivage + analyse en temps réel - Envoi vers HDFS + HBase simultanément

    3️⃣ Fan-in (Convergence multiple)

    Principe : Plusieurs sources ou agents envoient leurs événements vers un seul canal ou destination.

    ┌──────────┐
│ Source 1 │────┐
└──────────┘    │
                │     ┌──────────┐      ┌──────────┐
┌──────────┐    ├────▶│  Canal   │─────▶│   HDFS   │
│ Source 2 │────┤     │  Unique  │      │          │
└──────────┘    │     └──────────┘      └──────────┘
                │
┌──────────┐    │
│ Source 3 │────┘
└──────────┘

    Cas d'usage : - Centralisation de logs depuis plusieurs serveurs web - Agrégation de données de plusieurs data centers

    🖼️ [Illustration suggérée] : Plusieurs sources convergeant vers un seul canal (forme d'entonnoir).

agent1.channels.ch1.transactionCapacity = 100

    📘 Partie 3 : Écosystème Spark

    3.1 Contexte et motivations

    ⚠️ Limites de Hadoop MapReduce

    Problèmes identifiés :

    1. ❌ Latence élevée - MapReduce écrit systématiquement les résultats intermédiaires sur disque (HDFS) - Performances médiocres pour traitements complexes et itératifs

    2. ❌ Pas adapté au temps réel - Besoin de rapidité : applications modernes nécessitent des temps de réponse quasi interactifs

    3. ❌ Mauvaises performances pour algorithmes itératifs - Explosion des algorithmes itératifs (Machine Learning, Graphes) - Algorithmes ML (k-means, régression) nécessitent plusieurs itérations sur les mêmes données - MapReduce relit et réécrit les données à chaque itération

    4. ❌ Modèle de programmation bas niveau - MapReduce impose un modèle map/reduce rigide - Besoin d'une programmation plus simple et expressive

    5. ❌ Pas de support streaming - Systèmes modernes exigent des traitements streaming et quasi temps réel (logs, IoT, réseaux sociaux)

    6. ❌ Besoin d'un moteur unifié - Batch, streaming, ML, graphes nécessitaient des outils séparés

    🎯 Besoin : Un framework rapide, flexible et unifié

    3.2 Origine et évolution de Spark

    📅 Chronologie

    2009 : Développement initial au laboratoire AMPLab de l'Université de Berkeley - Conçu comme alternative plus rapide et flexible à MapReduce

    2013 : Don à la Fondation Apache - Devient rapidement l'un des projets les plus actifs de l'écosystème Big Data

    Aujourd'hui : Largement adopté par : - Entreprises (Netflix, Uber, Airbnb, etc.) - Universités - Centres de recherche

    3.3 Définition d'Apache Spark

    Apache Spark est un framework open-source unifié pour le traitement de données massives (Big Data).

    Caractéristiques : - ⚡ Rapide : Calcul en mémoire (in-memory processing) - 📈 Évolutif : Peut gérer de petits à très gros clusters - 🎨 Polyvalent : Supporte multiples types de traitement

    Performance : - Jusqu'à 100 fois plus rapide que Hadoop MapReduce pour certaines tâches itératives

    🎯 Domaines d'excellence de Spark

    ✅ Traitement batch (par lots) - ETL, transformation de données - Agrégations complexes

    ✅ Streaming en temps réel - Analyse de flux continus - Traitement quasi temps réel

    ✅ Requêtes SQL - Requêtes interactives sur grands volumes

    ✅ Machine Learning - Algorithmes ML distribués - Entraînement de modèles

    ✅ Traitement de graphes - Analyse de réseaux sociaux - Algorithmes de graphes (PageRank, etc.)

    💻 Langages supportés

    Spark supporte plusieurs langages :

    • ✅ Scala (langage natif de Spark)
    • ✅ Java
    • ✅ Python (PySpark)
    • ✅ R (SparkR)
    • ✅ SQL (Spark SQL)

    💡 Cette flexibilité permet aux développeurs d'utiliser le langage de leur choix !

    3.4 Caractéristiques principales de Spark

    ⚡ 1. Calcul en mémoire (In-memory Computation)

    Principe : - Spark stocke les données dans la mémoire vive (RAM) des serveurs - Accès ultra-rapide aux données - Évite les lectures/écritures disque répétées

    Avantage : - ✅ Accélération considérable de la vitesse des analyses - ✅ Particulièrement efficace pour les algorithmes itératifs

    Comparaison :

    MapReduce : Disque → Calcul → Disque → Calcul → Disque
Spark     : Disque → RAM → Calcul → Calcul → Calcul → Disque

    🖼️ [Illustration suggérée] : Diagramme comparant MapReduce (multiples accès disque) vs Spark (données en mémoire).

    🔄 2. Traitement distribué utilisant la parallélisation

    Principe : - Les données sont partitionnées sur plusieurs nœuds - Les calculs s'exécutent en parallèle sur ces partitions - Utilise pleinement les ressources du cluster

    Structure : - Driver : Coordonne l'exécution - Executors : Exécutent les tâches sur les partitions

    💡 Scalabilité : Peut passer de 1 machine à des milliers de nœuds

    📊 3. Abstraction de données : RDD, DataFrame, Dataset

    Spark fournit trois niveaux d'abstraction pour manipuler les données :

    RDD (Resilient Distributed Dataset)

    • Abstraction de bas niveau
    • Collection distribuée et immuable d'objets
    • Tolérant aux pannes (Resilient)
    • Utilisé en Scala/Java/Python

    DataFrame

    • Abstraction de moyen niveau
    • Données organisées en colonnes nommées (comme une table SQL)
    • Optimisations automatiques (Catalyst Optimizer)
    • API disponible en Python, Scala, Java, R

    Dataset

    • Abstraction de haut niveau (Scala/Java uniquement)
    • Combine avantages de RDD (type-safety) et DataFrame (optimisations)
    • Fortement typé

    💡 Recommandation : Utiliser DataFrame/Dataset pour la plupart des cas d'usage (meilleures performances)

    🌐 4. Framework unifié

    Principe : Spark fournit un seul framework pour :

    • Spark Core : Traitement batch
    • Spark SQL : Requêtes SQL et DataFrames
    • Spark Streaming : Traitement de flux temps réel
    • MLlib : Machine Learning
    • GraphX : Traitement de graphes

    Avantage : - ✅ Pas besoin d'apprendre plusieurs outils - ✅ Code réutilisable entre différents types de traitement - ✅ Partage de données entre les modules

    🖼️ [Illustration suggérée] : Schéma montrant Spark Core au centre avec 4 modules (SQL, Streaming, MLlib, GraphX) autour.

    🔌 5. Support de multiples sources de données

    Spark peut lire et écrire depuis/vers :

    Stockage distribué : - ✅ HDFS - ✅ Amazon S3 - ✅ Azure Blob Storage - ✅ Google Cloud Storage

    Bases de données : - ✅ Cassandra - ✅ HBase - ✅ MongoDB - ✅ Bases SQL (via JDBC)

    Formats de fichiers : - ✅ Parquet, ORC (optimisés) - ✅ CSV, JSON - ✅ Avro - ✅ Texte brut

    Streaming : - ✅ Kafka - ✅ Flume - ✅ Kinesis

    🛡️ 6. Tolérance aux pannes

    Mécanisme : Lineage (lignage)

    Principe : - Spark enregistre la séquence de transformations (DAG - Directed Acyclic Graph) - En cas de perte de partition : - Spark peut recalculer uniquement les partitions perdues - Utilise le lineage pour retrouver la séquence de transformations

    Avantage : - ✅ Pas besoin de réplication de données en mémoire - ✅ Récupération rapide en cas de panne

    ⚙️ 7. Lazy Evaluation (Évaluation paresseuse)

    Principe : - Les transformations ne sont pas exécutées immédiatement - Spark construit un plan d'exécution optimisé (DAG) - L'exécution réelle se déclenche uniquement lors d'une action

    Types d'opérations :

    Transformations (lazy) : - map(), filter(), groupBy(), join() - Créent de nouveaux RDD/DataFrame - Ne déclenchent pas de calcul

    Actions (eager) : - count(), collect(), save(), show() - Déclenchent l'exécution du DAG - Retournent un résultat ou écrivent sur disque

    Avantage : - ✅ Optimisations globales (fusion d'opérations) - ✅ Réduction du nombre d'étapes

    1. Driver

    Rôle : Cerveau de l'application Spark

    Responsabilités : - Héberge le SparkContext - Transforme le code utilisateur en plan d'exécution (DAG) - Planifie les tâches - Distribue le travail aux Executors - Collecte les résultats

    2. SparkContext

    Rôle : Point d'entrée de l'application

    Fonctions : - Établit la connexion au cluster - Gère la configuration de l'application - Permet d'interagir avec le cluster

    3. Cluster Manager

    Rôle : Gestionnaire de ressources du cluster

    Types supportés : - Standalone : Gestionnaire simple intégré à Spark - YARN : Gestionnaire Hadoop - Mesos : Gestionnaire Apache Mesos - Kubernetes : Orchestrateur de conteneurs

    Responsabilités : - Alloue les ressources (CPU, mémoire) - Démarre les Executors - Surveille l'état du cluster

    4. Executors

    Rôle : Travailleurs qui exécutent les tâches

    Caractéristiques : - Processus JVM s'exécutant sur les nœuds workers - Chaque Executor a sa propre mémoire et CPU - Exécutent les tâches envoyées par le Driver - Stockent les données en cache (si demandé) - Rapportent l'état des tâches au Driver

    🖼️ [Illustration suggérée] : Architecture Spark avec Driver au sommet, Cluster Manager au milieu, et plusieurs Executors en bas.

    🔄 Flux d'exécution d'une application Spark

    Étapes :

    1. Création du SparkContext - Le Driver démarre et crée le SparkContext - Connexion au Cluster Manager

    2. Allocation des ressources - Le Cluster Manager alloue les ressources - Démarre les Executors sur les nœuds workers

    3. Distribution du code - Le Driver envoie le code (JAR/Python) aux Executors

    4. Construction du DAG - Le Driver transforme le code en plan d'exécution (DAG) - Optimisations appliquées

    5. Planification des tâches - Le DAG est divisé en stages et tasks - Les tâches sont envoyées aux Executors

    6. Exécution - Les Executors exécutent les tâches - Traitement des partitions de données

    7. Collecte des résultats - Les Executors renvoient les résultats au Driver - Le Driver agrège et retourne le résultat final

    from pyspark.streaming import StreamingContext

ssc = StreamingContext(sc, 10)  # Batch interval de 10 secondes

ssc.start()
